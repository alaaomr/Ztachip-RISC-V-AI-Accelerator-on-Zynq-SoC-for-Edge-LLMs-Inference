Overview

This document lists every file we modified or created when porting the open-source ztachip AI accelerator from the Arty A7-100T development board to the Xilinx Zynq ZC702. Each entry explains WHAT was changed, WHY it was needed (in plain English), and where the file lives.

Two big architectural decisions shape everything below:

  1. Keep the VexRiscv soft-core CPU inside the FPGA fabric (PL). The ARM Cortex-A9 (PS) in the Zynq is used ONLY to provide DDR3 memory and clock generation — it does NOT control ztachip. This means all existing ztachip software keeps working unchanged.
  2. The PS-to-PL link is a single 64-bit AXI3 slave port (S_AXI_HP0). The ztachip DMA engine writes into PS-side DDR3 over this port. M_AXI_GP0 is disabled (ARM does not poke ztachip registers).

1. RTL changes (hardware description)

1.1 HW/src/config.vhd — MODIFIED

Change: exmem_data_width_c from 128 to 64.

Why: On the original Arty A7 the ztachip DMA talked to a Xilinx MIG (memory controller) over a 128-bit bus. On Zynq the AXI HP0 port maxes out at 64 bits. Changing this constant tells ztachip to issue 64-bit AXI bursts instead of 128-bit, matching the new port width.

1.2 HW/simulation/mem64.vhd — MODIFIED

Change: constant RAM_SIZE from 16000 words (128 KB) to 131072 words (1 MB).

Why: The default simulated DDR3 was only 128 KB. The LLM kernel tests (e.g., test_llm_rms with N=576) allocate hundreds of KB through malloc. Without this bump the linker fails with "region RAM overflowed". 1 MB is generous and works for all kernel tests we care about in simulation.

1.3 HW/simulation/tb_main.vhd — NEW FILE

Change: Created a top-level testbench wrapper that generates a 250 MHz clock and feeds it into the existing main testbench's clk input port.

Why: The original main.vhd declares clk as an INPUT port, expecting an external simulator to drive it. When we launched the sim with main as top, nothing drove clk, so every signal stayed at U (undefined). The new tb_main wrapper is what gets driven as the true sim top — it has no ports and generates the clock internally.

1.4 HW/src/test_llm.cpp — guarded with #ifndef SIMULATION

Change: Wrapped 5 functions in #ifndef SIMULATION blocks so they're excluded from the sim build: test_llm_dot_product, test_llm_dot_product2, test_llm_quantize, test_llm_matmul_q4, test_llm_matmul_q8, and the test_llm() wrapper.

Also reduced sine/cosine outer loops from max <= 50.0 to max <= 2.0 when SIMULATION is defined.

Why: Three of these functions use the GGUF class from gguf.cpp, which depends on C++ stdlib features we don't link in the sim build. Two others (matmul_q4, matmul_q8) allocate ~3.5 MB heap each and would take many hours in xsim. dot_product loops 1023 times. Guarding lets us keep the rest of test_llm.cpp without dragging in unwanted symbols. Sine/cosine had 50 outer iterations which alone would take 30+ minutes in sim.

2. New ZC702 top-level + Block Design

2.1 HW/examples/ZC702/main_zc702.v — NEW FILE

Change: Created a new Verilog top-level module that replaces the original Arty A7 main.v.

Key wiring:

  • Instantiates zynq_system_wrapper (PS block design wrapper).
  • Instantiates soc_base (VexRiscv + ztachip).
  • Connects ztachip DMA → S_AXI_HP0 AXI3 slave, with safe truncation of ARLEN/AWLEN from 8 to 4 bits (ztachip max burst = 9, AXI3 limit = 16, so safe).
  • All four clocks come from PS FCLK0/1/2/3 — no external oscillator, no clk_wiz needed.
  • UART, Camera, VGA, Ethernet are stubbed (tied off or APB stub: PREADY=1, PRDATA=0, PSLVERROR=0).
Why: The Arty A7 main.v expects external DDR3 pins, a 100 MHz oscillator, clk_wiz, camera connector, VGA pins, etc. — none of which apply to ZC702. The new top-level is a minimal port focused on getting LLM running, with peripherals we don't need stubbed for simplicity.

2.2 HW/examples/ZC702/zynq_ps_bd.tcl — NEW FILE

Change: Created a Vivado Tcl script that builds the Zynq PS block design from scratch.

It configures the PS7 IP with:

  • FCLK0 = 100 MHz (was 125, reduced to fix timing — see section 4.2)
  • FCLK1 = 250 MHz, FCLK2 = 24 MHz (camera), FCLK3 = 25 MHz (VGA)
  • S_AXI_HP0 enabled, 64-bit data width, AXI3 protocol
  • PCW_USE_M_AXI_GP0 = 0 (critical — disables unused master port)
  • assign_bd_address for HP0_DDR_LOWOCM (maps PS DDR3 into HP0 address space)
  • FIXED_IO and DDR exposed as BD ports (Vivado handles MIO/DDR3 pinout automatically)
Why: Without PCW_USE_M_AXI_GP0=0, Vivado emits a BD validation error (M_AXI_GP0_ACLK unconnected). Without assign_bd_address, ztachip DMA transactions to DDR fail at runtime even though everything builds cleanly. Both are easy to miss.

2.3 HW/examples/ZC702/main_zc702.xdc — NEW FILE

Change: Minimal constraints file — just enables bitstream compression.

Why: On Zynq, the PS DDR3 and MIO pin assignments are baked into the Zynq silicon itself — Vivado infers them from the Block Design's apply_board_preset call. There are no user-facing pins to constrain in our minimal port (Ethernet, UART, camera all stubbed).

2.4 HW/examples/ZC702/create_project_zc702.tcl — NEW FILE

Change: One-shot Vivado project creation script. Creates the project, adds all ztachip RTL files, generates FP32 IPs, sources the BD script, and generates the BD wrapper.

Why: Building this by hand in Vivado IP Integrator takes ~30 minutes of clicking and is error-prone. A Tcl script is reproducible, version-controllable, and takes seconds to re-run if something goes wrong. The -force flag on create_project lets us safely re-run after errors.

4.2 Implementation result — TIMING FAILED

WNS (Worst Negative Slack) = -1.449 ns at 125 MHz. This means the longest combinational path needs 9.449 ns to settle but only gets 8 ns (one 125 MHz clock period). Real silicon would produce wrong results at this frequency.

Fix: Lower FCLK0 from 125 MHz to 100 MHz (10 ns period). Estimated new WNS = +0.551 ns (PASS). Script run_step5_fix_timing.tcl is ready to apply this — not yet run because the board is not on hand.

Why timing failed: On Artix-7 (Arty), the design met timing because of better routing flexibility. Zynq XC7Z020 has tighter constraints due to the PS hard block consuming space. 100 MHz gives us a comfortable margin while still being plenty fast for LLM inference.

5. Simulation infrastructure

5.1 SW/sim/test_llm_main.cpp — NEW FILE

Change: New simulation entry point (replaces the original sim/test.c). Calls 8 LLM kernel tests in light-to-heavy order so the user sees led_out tick up quickly.

Why: The original sim/test.c ran kernel_test_exe() from the vision app — a simple "add 1 to a tensor" operation. We're verifying an LLM, so we need to run LLM-specific math. Each kernel call sets APB[APB_LED] after it passes, which the user watches in the Vivado waveform window.

5.2 SW/sim/linker.ld — MODIFIED

Change:

  • RAM length: 128k → 1024k
  • Heap size: 4000 bytes → 524288 bytes (512 KB)
  • Stack size: 8000 → 32768
Why: LLM tests allocate several hundred KB through malloc. With the original 4 KB heap, even one test_llm_rms call would fail. We also bumped total RAM because C++ stdlib exception-handling code adds ~150 KB to the text section. 1 MB matches our bumped simulated DDR3 size.

5.3 SW/makefile.sim — MODIFIED

Change: Added these source files to the SRCS list:

  • base/util.c (for randInit, randGen used by tests)
  • src/test_llm.cpp (the kernel tests themselves)
  • apps/llm/kernels/llm.m.c (hardware LLM kernels)
  • apps/llm/reference/llm_ref.c (reference C implementations)
  • sim/test_llm_main.cpp (new entry point)

Also fixed src/soc.c → src/soc.cpp (typo in original).

Why: The original makefile.sim only compiled enough for the simple vision test. We need the LLM kernels (both ztachip versions and reference C versions) so the test program can compare them.

5.4 HW/examples/ZC702/run_sim_build.sh — NEW FILE

Change: Shell script that performs all 4 simulation build steps:

  1. Auto-fix the soc.c → soc.cpp typo in makefile.sim
  2. Build the ztachip kernel compiler (the .m → .m.c translator)
  3. Compile all kernel files (.m → .m.c)
  4. Compile the RISC-V firmware → ztachip_sim.hex
Why: Each step depends on the previous one. A single script means Eslam types one command to rebuild after any change — no order to remember.

5.5 First successful sim — VISION KERNEL TEST

After all the above plumbing, the first simulation produced this output:

  • led_out counted 0 → 1 → 2 → 3 → … → 8 in ~1.5 ms of simulated time
  • Each increment = one kernel_test_exe() iteration passed
  • Proved end-to-end: RISC-V boots → executes program → talks to ztachip via DMA → receives correct results

5.6 Switch to LLM kernel sim

After the vision sim worked, we switched the firmware to run LLM kernels via test_llm_main.cpp. The LLM kernels are 3-5x heavier than vision so simulation takes proportionally longer. Tests reordered lightest-first so progress is visible early.

6. Critical blocker — model file transport

6.1 The problem

The original ztachip downloads SMOLLM2.ZUF via TFTP from 10.10.10.10 over Ethernet. See SW/apps/llm/gguf/zuf.cpp → ZUF::Open() → NetTftpDownload(...).

On our ZC702 port, the Ethernet IP (axi_ethernetlite) was stubbed out in main_zc702.v for simplicity. So NetTftpDownload has nothing to talk to and will fail.

6.2 Chosen workaround: JTAG / XSCT pre-load

Instead of fixing Ethernet, we'll:

  1. Modify ZUF::Open to skip TFTP and read the model from a fixed DDR3 address (e.g. 0x10000000).
  2. Pre-load the 67 MB SMOLLM2.ZUF file into that address via the Vivado HW server (XSCT script over JTAG) before releasing VexRiscv from reset.
  3. Boot VexRiscv. chat() calls modified Open() which validates the ZUF header at the known address — the rest of the LLM pipeline is unchanged.

Expected transfer time: 1-2 minutes (JTAG is slow but 67 MB is small). Alternatives considered: UART (80 min, too slow), SD card (PS rework needed), re-enable Ethernet via PS GEM (largest scope change). All rejected.
